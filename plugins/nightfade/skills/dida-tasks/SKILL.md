# dida-tasks：杂乱想法看板

目的是减少注意力切换：念头冒出来先落到清单里，当下不展开；该想的时候再集中处理。

脚本：`${CLAUDE_PLUGIN_ROOT}/skills/dida-tasks/scripts/aitasks.mjs`，下面用 `at` 代指 `node ${CLAUDE_PLUGIN_ROOT}/skills/dida-tasks/scripts/aitasks.mjs`。清单 ID 等本机配置在同目录的 `config.local.json`（不进仓库，格式见 `config.example.json`）。脚本复用本机 dida CLI（`/opt/homebrew/bin/dida`）的登录态；报未登录时让用户在终端运行 `! dida auth login`。

## 看板结构

列只表示状态，领域用标签。

| 列 | 键 | 放什么 |
|---|---|---|
| 📥 收件箱 | `inbox` | 刚冒出的念头，一行就够，不加工 |
| 🎯 进行中 | `doing` | 正在动手做的事，不限条数，由用户自己决定放什么 |
| 📌 待办 | `todo` | 具体、能直接动手的小事，不限条数，有期限就设截止日期 |
| ⏳ 等条件 | `waiting` | 写明了重新考虑条件或日期的事，条件写进内容 |
| 🅿️ 以后再说 | `later` | 值得留、但没有明确条件的事 |
| ✅ 已完成/放弃 | `closed` | 结束的事，留着追溯 |

**临时列**：用户会为短期项目临时加列，比如为一次旅行加「✈️ 某某行」，项目结束后用户自己删。这类项目的任务都放进临时列，换列时直接用列名关键词，如 `at move <任务> 某某行`。临时列被删后，残留任务按常规列重新分。

标签只用这六个：`工作` `摄影` `健康` `学习` `生活` `投资`。

## 命令

| 场景 | 命令 |
|---|---|
| 看全板 | `at list` |
| 记一条 | `at add <标题> [--content 内容] [--tags 摄影] [--col inbox] [--due 2026-11-15]` |

日期写法：`2026-11-15` 是全天任务；`'2026-11-15 14:30'` 带具体时间，按本机时区（可在配置里用 `timeZone` 指定，自动处理夏令时）。时间里有空格，要加引号。加 `--remind` 会在截止时间弹提醒；用户说「提醒我」时用带时间的 `--due` 加 `--remind`，没说几点就默认上午 10:00，并在回复里说明。重复任务加 `--repeat daily|weekly|monthly`（也可以直接给 RRULE），起始时间用 `--due` 设成第一次提醒的时间。
| 换列 | `at move <任务ID或标题片段> <inbox\|doing\|todo\|waiting\|later\|closed>` |
| 改内容、标签或日期 | `at edit <任务ID或标题片段> [--title ..] [--content ..] [--tags ..] [--due 2026-11-15\|none]`，`--due none` 清除日期 |
| 完成 | `at done <任务ID或标题片段> [--note 说明]` |
| 放弃 | `at abandon <任务ID或标题片段> [--note 放弃原因]` |
| 删除 | `at delete <任务ID或标题片段>`，只删误建的，正常结束用 done 或 abandon |

- 标题片段匹配到多条时脚本会报错并列出候选，改用任务 ID
- `done` 和 `abandon` 会先把任务移到「已完成/放弃」列，再写评论，再标完成（status 2）或放弃（status -1）
- `list` 只列未结束的任务；已结束的在滴答 App 里看
- dida CLI 自带命令不能换列，脚本是直接调接口传 `columnId`

## 目标和执行项

两个清单分工：**「🎯目标」放要达成的结果，「🤖AI Tasks」放为它做的执行项**。目的是不把执行当成目标，避免陷进执行细节。

操作目标清单：所有命令加 `--board goals`，比如 `at list --board goals`、`at add <标题> --board goals --col quarter`。目标板的列键：

| 列 | 键 | 放什么 |
|---|---|---|
| 🌅 长期 | `long` | 多年的方向 |
| 📅 今年 | `year` | 今年要达成的，新建目标默认放这里 |
| 🎯 本季度 | `quarter` | 本季度重点推进的 |
| ✅ 已达成/放弃 | `closed` | 结束的目标 |

**目标怎么写**：标题写成结果，不写成动作（写「开会能跟上 80% 以上、能主动发言」，不写「每天练英语」）。内容简洁、有格式，没有的部分就不写：

```
**达成**
- 一条一个标准

**现状**
- 一条一个要点
```

每条要点一短句，不写成段落。AI 拟的达成标准在「**达成**」后面标〔AI〕。

时间范围由所在的列表示，不写；「为什么」只在用户明确说过、而且一句话能说清时才写。

目标的标题和内容只用用户的原话和用户确认过的内容；AI 帮着拟的标准或拆解，先给用户看，确认后再写。

**关联**：AI Tasks 里服务于某个目标的执行项，内容第一行写 `目标：<目标标题>`。新建执行项时，如果明显属于某个目标就加上；拿不准就问用户。纯生活杂事不用挂目标。临时列（如某次旅行）整体对应一个目标时，列里的任务不用逐条写。

## 平时：随手记

用户在对话里冒出与当前话题无关的念头，或说「记一下」：

1. 用用户的原话写成一行标题，必要的补充放 `--content`，打一个领域标签
2. `at add` 进收件箱
3. 回复一句「记进收件箱了」，**不展开分析，回到原来的话题**

不要替用户把念头加工成计划、拆步骤或给建议。用户明确要求讨论时才展开。

**只记用户自己的念头和用户同意的事。** AI 自己想到的后续行动、检查项、建议，不直接写进清单：先在回复里列出来问用户，用户同意的才记。

## 每周整理

用户说「整理 AI Tasks」「每周整理」时：

1. `at list` 和 `at list --board goals` 拉两个看板
2. 收件箱逐条给出建议（具体小事去「待办」，主线去「进行中」），用一张表：标题、建议去哪列、一句理由。去「等条件」的要写出具体条件或日期
3. 对照目标检查：每个「本季度」和「今年」的目标，至少有一条执行项在推进吗？没有的提出来，问是补一条执行项还是承认暂时搁置；「进行中」的执行项都能对应到某个目标吗？对应不上的问一句为什么在做
4. 「进行中」里很久没动的提出来问一句还做不做；「待办」里过了截止日期的提出来；收件箱和「以后再说」里不该有截止日期的，建议清掉
5. 「等条件」里条件已经到了的，提出来问用户要不要转「进行中」
6. 「以后再说」里放了很久、用户已经没感觉的，建议放弃
7. 用户确认后再执行 `move` / `abandon`，最后再 `at list` 给用户看结果

整理时不改用户的原话，只换列、补标签、补条件。

## 接口限速

滴答开放接口每分钟最多 100 次请求，超了返回 429 `rate_limit_exceeded`，和条目总数无关。脚本遇到 429 会等 60 秒自动重试，最多 3 次。

- 一次操作要调好几次接口（新建并放进指定列约 4 次，完成或放弃约 5 次），批量处理时每条之间停 3–4 秒
- 批量导入要记录已完成的条目，中断后从断点继续，不要整批重跑，否则会产生重复

## 边界

- **写操作只限 🤖AI Tasks 和 🎯目标。** 另外「📒随手记」由 `dida-jot` skill 负责写。其他所有清单（❗任务、📝事务备忘等，其中有和家人共用的）一律只读：可以查、可以引用，不新建、不修改、不移动、不完成、不删除。用户在当次对话里明确点名某个清单并要求修改时才例外，且只对那一次有效
- 不新建清单、不改清单本身（名称、分组、列），AI Tasks 和目标清单的列结构也只在用户要求时改
- 器材等已有文档记着结论和重新考虑条件的事，清单里只放一行和条件，细节以文档为准

## 和个人笔记库待办的分工

用户不常看个人笔记库里的待办文件（路径见 `config.local.json` 的 `notesTodos`）。具体要做的事都在 AI Tasks；笔记库只留多步骤的大项目清单和隐私内容，AI Tasks 里放一条入口指向它。新的个人待办记进 AI Tasks，不再写进笔记库。
