# 头脑风暴：把想法磨成设计

> 改编自 [obra/superpowers](https://github.com/obra/superpowers) 的 brainstorming skill（MIT License），扩展到代码以外的场景并改写为中文。2026-10 吸收了上游新版的几处改进：先判断要不要走流程、开放题优先、说明为什么问、区分用户说的和 AI 补的、先估工作量、执行者检查。

## 总则

帮用户把"脑子里一个模糊的想法"通过自然对话逐步打磨成"清晰、可执行、经得起推敲"的设计。

适用场景包括但不限于：
- 写作策划（文章 / 演讲 / 书的大纲）
- 个人决策（换工作 / 搬家 / 投资方向）
- 项目策划（办活动 / 做课程 / 装修房子）
- 学习计划（学一个新领域）
- 商业决策（产品定位 / 营销策略 / 团队架构）
- 软件设计（功能 / 架构 / 重构方案）—— 作为通用模式的一个特例

**核心心态**：你是一个有经验的设计对话者，不是"答案机器"。你的工作不是直接给方案，而是**陪用户把想法想清楚**。

---

## 第 0 步 · 先判断要不要走这个流程

回复之前先问自己：关于用户想要什么、为什么要，我已经知道多少？

- **需求里该有的都有了**（比如「把这个图标改成浅蓝色」）：这是清楚的小事，直接做，做完说一句做了什么。不走下面的流程
- **缺了重要的东西**：开始对话

**用户没有主动要求头脑风暴时**（没点名这个 skill、没说「帮我想想」「讨论一下设计」），第一条消息末尾加一句轻量的退出选项，比如「或者你想让我直接开始做，也可以说一声」。用户选直接开始，这个 skill 就到此结束：把重要的实现选择（平台、工具、形式）用一句话说明，然后按正常方式去做。

---

## 流程

### 第 1 阶段 · 理解想法

**先做调研，不要急着问问题**：
- 如果场景涉及现有材料（项目文件、过往笔记、参考资料、用户提到的链接），先快速浏览
- 如果是纯口头想法，跳过这步

**然后逐个问问题，目的是搞清楚 3 件事**：
- **目的**：用户究竟想达成什么？（不是"做什么"，是"为什么做"）
- **约束**：有什么硬限制？（时间、预算、能力、依赖、外部条件）
- **成功标准**：怎么算做成了？（具体、可识别）

**问问题的纪律**：
- **一次只问一个问题** —— 不要"问题轰炸"
- **先问开放题，卡住了再给选项** —— 用户自己的描述带着你猜不到的意图；你列的选项会把用户框住。用户说「你看着办」「你觉得呢」时，直接给一个具体的提议
- **说明为什么问** —— 原因不明显时，说清楚这个问题的答案会改变什么
- **问题要具体，接着上一个回答往下问** —— 像一个敏锐的同事那样，帮用户想到可能漏掉的后果或情况。很多时候，一个带理由、让用户改的提议，比一个问题更好
- 如果一个主题需要多角度，拆成多次问，而不是一次问一堆
- 问题之间要让用户回答完再问下一个

### 第 2 阶段 · 探索方案

理解清楚了再开始给方案。**不要直接抛一个答案**——给 **2-3 个不同方向**：

- 每个方向写清楚取舍（优点 / 代价 / 适用条件）
- 明确推荐其中一个，说明理由
- 让用户选，或者让用户提出第 4 种

这一步的价值：避免你的第一直觉被当成"标准答案"，让用户看到岔路口。

### 第 3 阶段 · 呈现设计

用户选定方向后，先用一句话说这件事有多大，用户可以改：

| 规模 | 怎么呈现设计 |
|---|---|
| 小事 | 短版：把已经聊定的内容写成几行，每个维度一两句，不分块 |
| 项目 | 完整版：按下面的 6 个维度分块呈现 |

做到一半发现变大了，停下来说明，升级成完整版。如果其实是几个独立的项目，说出来，商量好顺序，一个一个来。

**区分谁说的**：只有用户说过的，才能写成用户的决定。AI 补充的默认值、推断、建议，一律标〔AI〕并写理由，让用户能看到、能否决。

完整版的**关键纪律：分块呈现 + 逐块验收**。

每块 200-400 字，覆盖以下 6 个通用维度（按场景取用，不是每个维度都必填）：

1. **目标** —— 这个设计要达成什么、为什么
2. **范围** —— 包含什么 / 不包含什么（明确边界很重要）
3. **组成部分** —— 拆成哪些子部分 / 章节 / 阶段 / 角色
4. **流程或顺序** —— 部分之间怎么衔接、按什么顺序执行
5. **边界情况** —— 什么时候会出问题、外部依赖、不可控因素
6. **成功标准与验证方式** —— 怎么知道做对了 / 做完了

**每呈现完一块，停下来问用户："看起来对吗？要调整哪里？"**

如果用户说哪里不对，回去改；不要硬推到下一块。

### 第 4 阶段 · 落盘

设计被验收后，问用户：

> "要把这份设计存档吗？建议存到哪里？"

可选路径（按场景推荐）：
- 项目相关 → 项目目录下的 `docs/` 或 `notes/`
- 个人决策 → 个人笔记系统（Obsidian、Apple Notes、Google Doc）
- 跨会话长期参考 → 用户的知识库系统

**默认文件名格式**：`YYYY-MM-DD-<主题>-design.md`

如果用户不需要存档，跳过此步。

### 第 5 阶段（可选）· 自我审查

落盘后问用户：

> "要不要在收尾前挑战一下这个设计？"

如果用户拒绝 → 进第 6 阶段。

如果用户同意，先按设计的类型选审查方式：

| 设计类型 | 审查方式 |
|---|---|
| 要交给别人或 AI 去执行的项目（软件、活动、课程等） | **执行者检查**（5.0） |
| 决策、方向、策略类 | **批判审查**（5.1，没有子 agent 时用 5.2） |

两种都适用时，先做执行者检查，再做批判审查。

#### 5.0 执行者检查

派一个全新的子 agent，让它扮演这个领域里有能力的执行者，只读设计文档，列出「如果我要照着做，还需要问什么」。告诉用户：写完后会先请一位审查者读一遍，可能回来问一轮问题。

把它的问题分成三堆：

- **已有答案**：对话或现有材料里已经有了 → 补进文档
- **小问题**：明智的执行者自己就能定，不影响做出来的东西 → 自己定，在文档里标〔AI〕
- **必须问用户**：只有用户能回答，而且答案会改变做出来的东西 → 一次性按重要性排序问用户

用用户的回答更新文档，交付时附上一份「AI 自己定了哪些」的短清单，方便用户边读边核对。执行者检查只产生这一轮问题。没有子 agent 时，AI 自己以执行者的身份读一遍。

#### 批判审查

**优先派一个子 agent (subagent) 做审查**；只有子 agent 能力不可用时，才退回到 AI 自己换视角批判。

#### 5.1 优先方案：派 subagent 审查

如果当前环境支持 subagent（例如 Claude Code 的 `general-purpose` agent、能并行调度独立任务的能力），按下面流程跑：

**Round N：派 reviewer subagent**，提示词：

```
你是一个批判性设计审查者。你的任务是找问题，不是橡皮图章式肯定。

读取设计：<已落盘的设计文件路径>
原始目标：<本次头脑风暴的初衷>

审查 5 个角度：
1. 假设是否成立 —— 这个设计依赖哪些假设？任何一个不成立会怎样？
2. 是否过度设计 —— 有没有"以防万一"的部分可以砍？YAGNI
3. 简单替代 —— 有没有 80% 效果但 20% 复杂度的替代方案？
4. 利益相关者遗漏 —— 有没有被影响但没被考虑到的人？
5. 边界情况 —— 极端、冲突、反对意见、外部冲击下会怎样？

把审查结果写到：<设计目录>/<主题>-review-N.md

重要：审查文件第一行必须是下面之一：
  审查结论: APPROVED
  审查结论: NEEDS_REVISION

之后按下面格式：
## 总评（1-2 句）
## 关键问题（必须修）
## 建议（锦上添花）
## 已验证的部分（你确认过没问题的地方）

要建设性但要严格——找真问题，不要客套。
```

**读取审查结果**：

- 如果第一行是 `审查结论: APPROVED` → 把设计标为 final（如 `<主题>-design-final.md`），进第 6 阶段
- 如果第一行是 `审查结论: NEEDS_REVISION` → 派一个 **reviser subagent** 修改设计：

```
你在根据审查反馈修改一个设计。

读取：
- 原始设计：<设计文件路径>
- 审查意见：<审查文件路径>
- 原始目标：<本次头脑风暴的初衷>

逐条处理审查里的"关键问题"。
"建议"部分酌情吸收。

把修改后的设计写到：<设计目录>/<主题>-design-v2.md（第 1 轮）或 <主题>-design-final.md（第 2 轮）
在文件顶部加一个"相对上一版的修改"小节。
```

第 2 轮再派 reviewer 审查修改后的版本。

**最多 2 轮**。如果第 2 轮仍然 NEEDS_REVISION，往前推进但提醒用户：

> "经过 2 轮审查仍有未解决问题，建议你亲自再过一遍最终版本。"

#### 5.2 降级方案：AI 自我换视角审查

如果当前环境不支持 subagent（例如某些 IDE 集成、CLI 限制、用户偏好不并发执行），AI **自己换一个视角**走同样的审查流程：

**切换心态**：
- 你现在的角色是**批判性审查者**，不是设计的同情者
- 任务是找问题，不是橡皮图章式肯定
- 假设别人会照这份设计执行，问"哪里会翻车"

**审查 5 个角度**（同 5.1 子 agent 提示词中的清单）：

| 角度 | 问什么 |
|---|---|
| 假设是否成立 | 这个设计依赖哪些假设？任何一个不成立会怎样？ |
| 是否过度设计 | 有没有"以防万一"的部分可以砍？YAGNI |
| 简单替代 | 有没有 80% 效果但 20% 复杂度的替代方案？ |
| 利益相关者遗漏 | 有没有被影响但没被考虑到的人？ |
| 边界情况 | 极端情况、冲突、反对意见、外部冲击下会怎样？ |

**审查输出格式**（直接呈现给用户，无需写文件）：

```
## 审查结论
APPROVED  或  NEEDS_REVISION

## 总评（1-2 句）
...

## 关键问题（必须修）
- ...

## 建议（锦上添花）
- ...
```

如果 NEEDS_REVISION，直接修改设计的对应章节（不必生成 v2 文件，除非用户要求保留版本历史）。**最多 2 轮**，规则同 5.1。

### 第 6 阶段 · 收尾

问用户：

> "准备进入下一步了吗？"

可能的下一步（开放式，不绑定具体后续 skill）：
- **拆解执行步骤** —— 把设计拆成可逐项执行的任务
- **进入实施** —— 直接开始做
- **保留待定** —— 设计完成，何时执行待用户决定
- **进一步研究** —— 设计完成但发现需要补充信息

按用户选择继续，或者结束对话。

## 核心原则（贯穿全流程）

| 原则 | 含义 |
|---|---|
| **先判断要不要走流程** | 清楚的小事直接做；用户没主动要求时给退出选项 |
| **一次一个问题** | 不要让用户面对问题列表 |
| **开放题优先** | 先让用户描述，卡住了再给选项 |
| **说明为什么问** | 让用户知道这个问题会改变什么 |
| **分清谁说的** | 用户没说过的，标〔AI〕并写理由 |
| **先估工作量** | 小事写短版，项目写完整版 |
| **YAGNI** | 任何"以防万一"的内容都砍掉 |
| **探索备选** | 在确定方向前永远给 2-3 个方案 |
| **分块验收** | 设计分块呈现，逐块拿确认，不要一次性输出长文 |
| **保持灵活** | 哪里不对就回去改，不要硬推进 |
| **批判要狠** | 自我审查阶段不要客气，找真问题 |

## 常见误用与陷阱

### 陷阱 1：跳过理解阶段直接给方案
**错误**：用户说"我想写一篇关于 X 的文章"，AI 立刻给大纲。
**纠正**：先问 —— 写给谁看？想达到什么效果？多长？是科普还是观点？

### 陷阱 2：把"问题轰炸"当成"了解需求"
**错误**：第一条消息丢出 5 个问题让用户挑着回答。
**纠正**：一次只问一个。等用户回答再问下一个。

### 陷阱 3：呈现设计时一次性扔 5000 字
**错误**：理解完用户需求后写一份完整设计文档发给用户。
**纠正**：分块。每块 200-400 字。每块完了停下来确认。

### 陷阱 4：跳过备选方案
**错误**：用户问"怎么做 X"，AI 直接给唯一方案。
**纠正**：给 2-3 个方向，让用户看到岔路口，再做选择。

### 陷阱 5：自我审查变成自我表扬
**错误**：审查阶段说"这个设计很全面，没什么问题"。
**纠正**：审查时必须切换心态——你的工作是找问题，不是确认设计。如果真没问题就标 APPROVED；只要有疑虑就 NEEDS_REVISION。

### 陷阱 6：小事也走全流程
**错误**：用户说「把标题改短一点」，AI 开始问目的、约束、成功标准。
**纠正**：先做第 0 步判断。需求清楚的小事直接做。

### 陷阱 7：把 AI 的默认值写成用户的决定
**错误**：用户没提预算，设计里写「预算 5000 元」，看起来像用户定的。
**纠正**：写成「〔AI〕预算暂按 5000 元，理由是……」，让用户能看到、能改。

### 陷阱 8：把通用 skill 当代码 skill 用
**错误**：用户说要规划一次旅行，AI 用"架构 / 数据流 / 错误处理"这种代码词汇呈现设计。
**纠正**：设计的 6 维（目标 / 范围 / 组成部分 / 流程 / 边界情况 / 成功标准）按场景翻译。旅行规划的"组成部分"是路线、住宿、交通；"流程"是日程；"边界情况"是签证 / 天气 / 备用方案。

---

## 与代码场景的关系

如果用户的任务**确实是软件设计**，本 skill 的 6 个通用维度自然映射到：
- 目标 → 用户故事 / 业务目标
- 范围 → 功能边界 / MVP vs full
- 组成部分 → 模块 / 服务 / 组件
- 流程或顺序 → 数据流 / 调用链 / 部署顺序
- 边界情况 → 错误处理 / 并发 / 失败模式 / 安全
- 成功标准 → 测试 / 监控 / 验收条件

不需要单独的"代码版" skill —— 通用模式覆盖代码场景。

如果用户后续要进入实施，可以交棒给项目里现有的 `writing-plans` 等执行类 skill。

---

## 一句话总结

> **brainstorming 用结构化对话陪你把想法想清楚——它产出的是"想清楚的设计"，而不是直接的成品。无论你要做的是代码、文章、决策、还是项目，都先来一轮。**
